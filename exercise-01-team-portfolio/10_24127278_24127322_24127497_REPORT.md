## 2. Exercise 01 architecture

### 2.1. Static multi-page design

The website consists of four HTML documents: a team home page and three member pages. Each portfolio has its own URL, and ordinary links connect the pages. Selecting a portfolio causes the browser to request another HTML document; the website does not use client-side routing.

This architecture matches the small number of pages and the primarily informational purpose of the exercise. It provides readable source files, requires no compilation or dependency installation, and can be served directly by Caddy. Essential content is available in HTML rather than being generated by JavaScript.

HTML defines content and document structure, CSS controls presentation and responsive layout, and JavaScript adds optional interactions. Keeping these responsibilities separate makes the implementation easier to understand and maintain.

The stylesheet separation avoids duplicating common styles while keeping page-specific rules identifiable. CSS custom properties provide consistent colors and visual tokens across all four pages.

Relative paths account for the member pages' nested location. For example, the home page loads `assets/css/main.css`, while a member page loads `../assets/css/main.css`. Display names are independent of filenames, so a member's name can appear in navigation and previews without renaming `member-1.html` or changing its links.

### 2.4. Architectural tradeoffs

The header and footer are repeated in each HTML document. This small amount of duplication avoids a template engine or JavaScript-generated navigation, but shared changes must be applied consistently across all four pages.

Member information is stored directly in HTML. `docs/CONTENT.md` supplies approved content during development, but editing that document does not automatically update the pages. Preview summaries are also maintained manually. This is manageable for three members and keeps essential content independent of JavaScript.

## 3. Website features

### 3.1. Team introduction and personal portfolios

The home page presents the team identity, areas of interest and three member cards. Each member page uses a consistent structure for the person's introduction, biography, categorized skills, education, personal projects and approved contact links where available. Header and footer links allow visitors to move between the team and individual profiles.

### 3.2. Responsive layouts

CSS Grid, Flexbox, fluid sizing and media queries adapt the presentation for different screen widths. Multi-column layouts on larger screens become stacked layouts on smaller screens. With JavaScript enabled, a compact navigation menu provides access to page links on narrow viewports.

### 3.3. Light and dark modes

A theme button allows visitors to select light or dark mode. Dark mode uses dark surfaces with neon accents, while light mode uses a brighter palette. Shared CSS variables apply the selected appearance consistently throughout the website.

### 3.4. Miniature member previews

Hovering over a member card or focusing a link within it reveals a compact portfolio-style summary containing the member's name, role and selected skills. The preview remains visible on devices without hover support. It is a styled HTML component, not an iframe or a live rendering of another page.

### 3.5. Interaction and visual effects

Cards and boxes use subtle border, shadow and movement effects to communicate interaction. Short page transitions accompany ordinary internal navigation. A grid/dot background, decorative terminal panels and a soft cursor glow reinforce the developer-oriented theme. Terminal commands are decorative text and do not execute commands on the computer.

### 3.6. Accessibility support

Semantic landmarks, logical headings, skip links, current-page indicators and visible focus styles support navigation. The mobile menu exposes its expanded state, and member previews respond to keyboard focus as well as hover. Reduced-motion preferences limit non-essential animation. These are implemented accessibility measures rather than a claim of independently certified compliance.

## 4. JavaScript behavior

The shared script loads with `defer`, allowing HTML parsing to complete before it enhances the interface. It does not render biographies or retrieve project data from a server.

| Interaction | JavaScript responsibility |
| --- | --- |
| Theme initialization and switching | Reads a saved preference from `localStorage`, otherwise follows the operating system's color preference. Updates `data-theme`, saves a new selection and synchronizes button labels and icons. Storage errors are caught. |
| Responsive navigation | Opens and closes the mobile menu, updates `aria-expanded`, closes after a link is selected and supports Escape with focus restoration. A viewport media query synchronizes desktop and mobile states. |
| Cursor glow | Uses pointer coordinates and `requestAnimationFrame` to update CSS custom properties. Tracking is enabled for a fine pointer when reduced motion is not requested. |
| Terminal feedback | Changes decorative member-selection text when a card receives pointer entry or keyboard focus, then restores the default text when the interaction ends. |
| Page transitions | Applies an exit state before ordinary same-origin `.html` navigation and loads the destination after 180 ms. Modified clicks, links with target/download attributes, same-page anchors and reduced-motion navigation retain normal behavior. |
| History restoration | Removes the exit state on `pageshow` so browser-history navigation does not leave a page faded out. |

The underlying navigation still consists of normal HTML links. Without JavaScript, essential content and page links remain available; theme controls and other script-dependent enhancements are not provided. No database connection, form submission or third-party API call is part of this website.

## 5. Development methodology

### 5.1. Documentation before implementation

Markdown documents established a shared specification before coding. `REQUIREMENTS.md` defined scope and acceptance criteria; `ARCHITECTURE.md` assigned file responsibilities; `DESIGN.md` guided responsive presentation and accessibility; and `TASKS.md` divided implementation into manageable phases. `AGENTS.md` established working rules for the coding agent, including preserving existing work and avoiding unsupported personal claims.

Member information was supplied through `CONTENT.md`. This separated content approval from interface implementation and allowed the agent to populate the pages using information provided by the team rather than inventing biographies or achievements.

### 5.2. Scoped AI-assisted implementation

The coding agent first inspected the specifications and explained the implementation approach. Development then proceeded in focused stages: static page structure, shared styling, responsive navigation, content integration and approved visual enhancements.

Prompts specified the required outcome and relevant constraints. For example, theme selection was requested as a user-controlled feature, while previews were refined to show member names and skills. This approach limited unintended scope expansion and made individual changes easier to evaluate.

### 5.3. Human review and refinement

The rendered website was reviewed by the project owner, with screenshots and specific feedback used to guide corrections. Review led to replacing a wireframe-like preview with meaningful profile information, adding light/dark selection and refining preview labels.

A preview styling issue also prompted versioning of the team stylesheet URL to avoid pairing updated HTML with an older cached stylesheet. This illustrates why rendered-product review is necessary in addition to source inspection.

The development process followed a repeated cycle: specification, scoped prompt, implementation, visual review and correction. The agent assisted with code, while human review determined content accuracy and design acceptance. Later approved enhancements extended the original static-page scope without changing the underlying multi-page architecture.

## 6. Local hosting with Caddy

### 6.1. Server selection

Caddy was chosen because its concise configuration is suitable for serving this small static website. Its file server can serve the existing HTML, CSS, JavaScript and icon files directly, without an application runtime or build process. Nginx would also be a valid choice; Caddy was selected for configuration simplicity, not because Nginx cannot support the exercise.

### 6.2. Server configuration

The submitted `Caddyfile` contains:

```caddyfile
http://localhost:8080 {
    bind 127.0.0.1
    root * .
    file_server {
        hide Caddyfile
    }
}
```

| Directive | Meaning |
| --- | --- |
| `http://localhost:8080` | Defines the local site address using HTTP on port 8080. |
| `bind 127.0.0.1` | Restricts the listener to the IPv4 loopback interface. |
| `root * .` | Sets the file-serving root to the working directory from which Caddy is started. |
| `file_server` | Enables serving files from that root, including the directory's `index.html`. |
| `hide Caddyfile` | Prevents the server configuration file from being served through HTTP. |

The loopback binding means that the website is accessible from the server computer, not automatically from other devices on the same network. The configuration hides `Caddyfile` specifically; it does not automatically hide other documentation or evidence files stored under the serving root.

### 6.3. Starting and accessing the website

With Caddy installed, run the following commands from the directory containing the exercise folder:

```sh
cd exercise-01-team-portfolio
caddy validate --config Caddyfile --adapter caddyfile
caddy run --config Caddyfile
```

The validation command checks the configuration, and the run command starts the foreground server. The working directory is important because the configured root is `.`. The website is then available at `http://localhost:8080`. Pressing Ctrl+C stops the foreground server.

### 6.4. Request handling

When the browser opens the local address, Caddy serves `index.html` from the configured root. The browser subsequently requests its stylesheets, script and favicon. When a member link is selected, the browser requests the corresponding document, such as `/members/member-1.html`, and resolves that document's relative asset paths.

```text
Browser requests http://localhost:8080
    → Caddy serves index.html
    → Browser requests linked CSS, JavaScript and icon files
    → Browser renders the team page
    → Selecting a member requests that member's HTML page
```

Caddy provides the HTTP serving layer; it does not generate the website content or execute the browser's JavaScript. This local deployment demonstrates that the website can be accessed through a web server rather than only by opening an HTML file directly.
