SANTAISHI-TEI / BLOCK 6 08

Workflow: save a dish

  1. Chef selects Save draft or PublishLock repeat submissions and show progress.
  2. Upload a newly selected photo, if anyPOST /api/dish-photos → validate → resize → Storage → public URL.
  3. Send dish fields through the shared clientPOST for creation; PATCH for edits. Include the photo URL.
  4. Authorize and validate on the serverSession → role → CSRF → permitted fields → business rules.
  5. Persist with Prisma and return the saved record{ ok: true, data: … } → close editor → refresh the board.

On failure: retain the form and show a useful error. A failed board refresh offers retry without repeating the save.

REST API contract

MethodResourcePurpose
GET/api/menuRead published dishes
POST/api/dishesCreate a dish
PATCH/api/dishes/:idChange supplied fields
PUT/api/dishes/:id/recipeReplace recipe
DELETE/api/dishes/:idArchive dish
POST/api/stock-operationsRecord stock change

Managed response envelopes

    "fields": { "name": "Required" }
  }

Illustrative payload excerpts. The frontend branches on code, not message.

JSON writes: application/json. Photo uploads: multipart/form-data with a browser-generated boundary.

SANTAISHI-TEI / BLOCK 6 10

Errors, loading and recovery

Three layers checked centrally

  1. Network: offline, timeout or connection failure.
  2. HTTP: unsuccessful status such as 401, 403 or 500.
  3. Application: HTTP 200 with ok: false.
StatusMeaning in this exercise
200Success or expected business failure
401 / 403Unauthenticated / forbidden
500Unexpected server failure
404Unknown API route

Each page loads its own content. Loading feedback and interaction locks prevent repeated actions.
